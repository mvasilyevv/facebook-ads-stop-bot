## 3. Корневые паттерны

**P1. Рассинхрон фронт↔бэк после UI-ребилда (доминирующий, ~10 багов).**
Самый массовый класс. Фронт переписан, но потеряны/разъехались контракты:
- Имена query-параметров (`alert_states`≠`alert_state` — M1; `hours`≠`from_iso` — L7; `offer_id`≠`cpa` — L4).
- Пути эндпоинтов (`DELETE /token` которого нет — L3).
- Shape ответов (`{ok,task_id,status}`≠`{ok,detail}` — L5/M3).
- Потерянная инициализация auth (apiKey=null, VITE_API_KEY не читается — H5).
- Мёртвые хуки-сироты, отвалившиеся от UI (useRulesPreview — L4/L14; useDashboardAlerts — L7).
Корень: после ребилда нет сквозной сверки сгенерированного OpenAPI-контракта с рукописными интерфейсами в `lib/api/*`; часть интерфейсов рукописная (не из `generated.ts`) и разъехалась.

**P2. Отсутствие глобального error-handling на money-путях фронта (L1, L13, M3, L12).**
`QueryClient` без `MutationCache.onError`, 0 `onError` в `lib/api/*`, `ConfirmDialog` без `catch`, страницы Drafts без toast вообще. Мутации (disable/delete/draft-confirm) падают молча — оператор не узнаёт о провале стопа. ObserverTab/TelegramTab сделаны правильно (try/catch+toast) — значит это регресс, а не стиль.

**P3. FSM-инварианты не закрыты по краям money-контура (H1, H2, H3, L2).**
Состояния `snoozed_until`, `disabled`, `claimed` имеют дыры:
- snooze не привязан к incident-токену → переживает закрытие инцидента (H1).
- disabled не имеет observer-driven reopen при внешней реактивации (H3); заявленная `reopen_reactivated_alert_state` не существует.
- bulk-sync метит FSM по входному списку, а не по применённому (H2).
- ручной `dis:` не доходит до `claimed` (L2).
Корень: FSM-переходы и сброс side-полей (snooze/disabled) не централизованы — `apply_fsm_transition` не трогает `snoozed_until`, reset только в enable-пути.

**P4. Auth-периметр непоследователен (M2, L6, H5).**
WS не покрыт middleware (scope-type guard в BaseHTTPMiddleware — M2); ephemeral-key прячет честный 503 (L6); фронт не передаёт ключ (H5). Read-GET и WS осознанно открыты, но WS не задокументирован как исключение.

**P5. Мульти-кабинет (этап 8) проброшен не везде (H4, L10, L11).**
`ad_account_id` есть в RunScanCycle/ExecuteGraphCall, но нет в ListCampaigns (L10); холодная вкладка кабинета не прогревает токен для мутации (H4); мёртвый старый клиент без ad_account_id (L11). Корень: миграция на мульти-кабинет неполная по периметру gRPC.

## 4. Приоритизированный план работы

Порядок: сначала money-критичные с реальной потерей денег, затем money-контур управления, затем UX-надёжность, затем чистка.

### Волна 1 — money-критичные FSM/мутации (чинить ПЕРВЫМ)
1. **H1** — snooze закрытого инцидента подавляет новый STOP. Прямая дыра: убыточный ад крутится без стопа до 2ч. Фикс минимальный (сброс `snoozed_until` при переходе в normal).
2. **H4** — холодная вкладка → перманентный fail pause/activate. Бьёт autostart bulk-activate (money-критичный автомат) и ручной pause в мульти-кабе. Ждать EAA-токен после goto.
3. **H2** — partial-bulk FSM-рассинхрон. Ложный `disabled` → observer слепнет → вечный пережог. Прокидывать `modified_ids`.
4. **H3** — FSM-залип в disabled при ручной реактивации. Реализовать reopen по delivery_status.

### Волна 2 — money-контур управления (фронт write-поверхность)
5. **H5** — apiKey=null → 401 на всех мутациях. Без этого весь ручной money-контроль из веб-UI мёртв в проде. Bootstrap из `VITE_API_KEY` в `main.tsx`.
6. **L1 + M3** — error-handling + toast на money-путях (disable/delete/draft). Глобальный `MutationCache.onError` + catch в ConfirmDialog. Закрывает «молчаливый провал стопа».
7. **L6** — не прятать 503 за ephemeral-key (даёт диагностируемость H5).

### Волна 3 — наблюдаемость и безопасность
8. **M2** — auth на WS `/ws/dashboard` (токен в handshake).
9. **M1** — серверный фильтр `alert_state` (страница Ads — заявленная ключевая функция).
10. **L2** — `dis:` → `claimed` (гигиена очереди/аудита).

### Волна 4 — мульти-кабинет и аналитика
11. **L10** — `ad_account_id` в ListCampaigns (UX live-refresh).
12. **L8** — единая семантика `active_ads_count`.
13. **L9** — try/except в ads_timeline + task_serializer (latent 500).

### Волна 5 — чистка контрактов и мёртвого кода
14. **L3, L4, L5, L7, L12, L13, L14** — починить/удалить разъехавшиеся хуки и типы фронта (привести к `generated.ts`).
15. **L11** — удалить мёртвый `clients/python_grpc/meta_api_client.py`.
