## Находки

### HIGH — форма чувствительности стоп-правил в mini отстаёт от модели web (нет slider'ов stop/warning % + live-preview)

- **Файл:** `frontend-mini/src/routes/offers/index.tsx:55-75` (сравнить с `frontend/src/components/offers/OfferRulesFields.tsx`)
- **Проблема:** web (компонент `OfferRulesFields.tsx`) использует модель `cpa_threshold` + `stop_percent_of_rule`/`warning_percent_of_stop` (ползунки чувствительности warning относительно stop) с live-preview реальных денежных порогов через `GET /offers/rules/preview` — тот же движок, что и боевой evaluator (комментарий в коде: "ТОЧНО совпадает с реальными срабатываниями"). Mini реализует только сырой `cpa_threshold`/`frequency_threshold` без ползунков и без preview. Верифицировано напрямую: в `frontend/OfferRulesFields.tsx` поля `stop_percent_of_rule`/`warning_percent_of_stop` присутствуют (строки 25-122), в mini `offers/index.tsx` — отсутствуют.
- **Impact:** владелец, настраивающий пороги автостопа с телефона, не управляет реальной чувствительностью (во сколько раз warning мягче stop) и не видит денежный preview порога перед сохранением — риск разойтись с ожиданиями по срабатыванию автостопа. Прямой потери денег/данных нет — PUT на бэке partial-update (`exclude_unset`), mini не отправляет отсутствующие поля → `stop_percent_of_rule`/`warning_percent_of_stop`, выставленные ранее через web, не затираются сохранением из mini.
- **Fix:** портировать `OfferRulesFields`/hook превью (`useRulesPreview` или аналог) в mini в адаптированном под bottom-sheet виде, синхронизировав список полей с моделью бэка.
- **Confidence:** high (верифицировано чтением обоих файлов).

### MID — Dashboard mini использует наивный локальный countdown вместо чтения adaptive-интервала из `observer:runtime`

- **Файл:** `frontend-mini/src/routes/index.tsx:43-54, 88-90`
- **Проблема:** `useScanCountdown` — таймер по `default_interval_seconds`, не читает `next_scan_at`/`scan_mode` из Redis `observer:runtime`, которые уже отдаёт бэк и которые использует web для отображения адаптивного интервала (CRITICAL/ELEVATED/CALM/IDLE режимы).
- **Impact:** обратный отсчёт до следующего скана в mini может визуально расходиться с реальным временем скана при включённом adaptive-interval — не прямой денежный риск, но снижает доверие к "живости" мониторинга с телефона в момент, когда важнее всего понимать, скоро ли следующая проверка убыточного ада.
- **Fix:** читать `next_scan_at` из `GET /observer/status` (как это делает web) вместо локального таймера от фиксированного интервала.
- **Confidence:** med.

### MID — тестовые дыры на error-путях money-экранов

- **Файлы:** `frontend-mini/src/tests/Dashboard.test.tsx`, `frontend-mini/src/tests/AdDetail.test.tsx:316-335`
- **Проблема:** нет теста на `isError`-ветку рендера Dashboard (что покажет владельцу экран при недоступном API — статы/спенд), нет теста реакции UI на отклонённую (ошибка сети/сервера) disable-мутацию, нет явного regression-теста, что кнопка disable/claim реально дизейблится на время `isPending` (только happy-path confirm/cancel протестирован).
- **Impact:** регрессия в error-handling money-действий (например, случайно убранный try/catch или снятая busy-блокировка) не будет поймана тестами — тот самый класс "тесты проверяют shape/happy-path, не семантику отказа", который уже приводил к CRIT в backend.
- **Fix:** добавить 3 теста — Dashboard `isError`-рендер с видимым error-state, AdDetail disable-мутация с отклонённым промисом (проверка что `tgAlert`/error показывается, а не тихий catch), тест что кнопка `disabled` во время `isPending` (защита от двойного тапа = дубль task в outbox).
- **Confidence:** med.

### LOW — `Number(p.spend) || 0` в данных для графика спенда схлопывает null/NaN/настоящий 0 в одно значение

- **Файл:** `frontend-mini/src/lib/api.ts:190`
- **Проблема:** точка временного ряда для SpendChart теряет различие "нет данных за бакет" vs "потрачено 0". Проверено: главная суточная сумма спенда (`stats.current_day_spend`), которую видит владелец как основную цифру, обрабатывается отдельно null-safe и в этот баг не входит — затронут только массив точек графика.
- **Impact:** минорное визуальное искажение тренда на графике (плоская линия вместо разрыва при пропуске данных), итоговую сумму не искажает.
- **Fix:** `Number.isFinite(Number(p.spend)) ? Number(p.spend) : null`, в компоненте графика рисовать разрыв на null-точках вместо нуля.
- **Confidence:** low.

### LOW — нет ручной enable-кнопки в AdDetail mini

- **Файл:** `frontend-mini/src/routes/ads/$fbAdId.tsx`
- **Проблема:** для объявления в состоянии `disabled` в mini доступны только Disable (не имеет смысла повторно) и Claim, нет ручного enable — в отличие от web, где есть отдельный enable-flow (в т.ч. через enable-рекомендации).
- **Impact:** функциональный пробел, не money-риск сам по себе (скорее наоборот — включение с толстого пальца на маленьком экране действительно рискованнее disable, так что отсутствие может быть осознанным решением). Владелец не может вручную включить объявление обратно с телефона, минуя TG-команду/десктоп.
- **Fix:** если решение осознанное (enable как более рискованное действие сознательно исключено из mobile UX) — зафиксировать явно в комментарии/доке; иначе добавить кнопку по аналогии с web enable-flow с обязательным confirm.
- **Confidence:** med.

## Зоны, проверенные и признанные чистыми

- **Клиентское суммирование кумулятивных `ad_metrics`** (аналог backend CRIT-1 про naive SUM) — не найдено. Все `.reduce()` в mini относятся к неденежным campaign-wizard счётчикам; `/dashboard/chart-data` уже агрегирован на бэке (DISTINCT ON), mini его не пересчитывает.
- **TMA-auth** — initData не валидируется на клиенте (корректно: клиентская проверка hash без секрета бота бессмысленна), передаётся на бэк как есть; Bearer хранится в localStorage с sessionStorage fallback; таймаут логина 15с; при 401 — явный error-state + retry-once, тихих пустых экранов не найдено.
- **Двойной тап на money-кнопках** — защищено: `const busy = disable.isPending || claim.isPending` блокирует обе кнопки одновременно (`frontend-mini/src/routes/ads/$fbAdId.tsx:50, 322, 335`), плюс `tgConfirm` перед disable. Верифицировано напрямую чтением кода.
- **Тач-таргеты** — `Button.tsx` гарантирует `min-h-[44px]` для стандартных размеров; исключение — размер `sm` (36px), используется только для второстепенных не-money действий.
- **Дублирование FSM-констант/лейблов мимо `@fb/shared`** — не найдено, `normalizeAlertState`/`ALERT_STATE_LABELS` импортируются из shared корректно.
- **Silent `?? 0` на основных money-полях** (спенд/CPL/CPR в карточках, суточная сумма) — не найдено; используется паттерн `null → "—"` через форматтеры `@fb/shared`, отличающий "нет данных" от нуля.

## Рекомендованный план

1. **HIGH (offers rules slider+preview)** — портировать в mini при следующем цикле работы над Offers-экраном; не блокер, т.к. существующие значения не затираются, но снижает качество решений владельца при настройке автостопа с телефона.
2. **MID (adaptive countdown, тестовые дыры)** — недорого чинить, взять в ближайший спринт тех-долга mini.
3. **LOW** — по возможности, не приоритет.

Общий вывод: в части денежных потоков (spend/CPL, disable-flow, защита от дубль-тапа, обработка 401) `frontend-mini/` сделан аккуратно и без CRIT/money-багов класса, который ранее находили в backend. Главный разрыв — функциональное отставание формы порогов от web-модели (slider + live-preview), не баг, а недопоставленная фича.
