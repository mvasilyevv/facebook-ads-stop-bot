# Модалка «Настроить пороги» для оффера

**Дата:** 2026-05-12
**Статус:** утверждён пользователем

## Контекст

Сейчас настройки per-offer порогов (warning/stop % для CPC/CPL/CPR) живут внутри модалки редактирования оффера (`OfferModal`). В прошлой итерации я завернул их в `<details>`-блок — пользователь отклонил такой UX:

> «Ой нет, разворачивание и сворачивание блока с настройками в Оффере — это ужасно, пусть лучше окно новое открывается!»

Требование: вынести пороги в отдельную модалку, которая открывается из отдельной колонки «Пороги» в карточке оффера.

## Цели

- Колонка «Пороги» в карточке/строке оффера между «Правила» и «Действия».
- Кнопка «Настроить пороги» в этой колонке — открывает модалку.
- Модалка содержит **только** 6 полей порогов + служебные кнопки.
- Полный паритет между `frontend/` (desktop) и `frontend-mini/` (TMA).
- Существующий API `GET/PUT /offers/:id/rules` не меняется.

## Не-цели

- Не меняем схему БД и Alembic-миграции.
- Не трогаем API-роутеры и Pydantic-схемы.
- Не переносим остальные правила из `OfferModal`.
- Не добавляем отдельный роут/страницу — именно модалка.

## Структура карточки оффера

Итоговый порядок колонок: **Код · CPA · Страна · Статус · Правила · Пороги · Действия**.

- Desktop: обычная таблица/строка с новой ячейкой.
- TMA: те же данные в адаптированном layout карточки.

## UX модалки

**Заголовок:** «Пороги оффера `<код>`».

**Подсказка сверху:** «По умолчанию warning 80%, stop 80%. Пустое поле = значение по умолчанию.»

**Поля (6 штук, парами):**

| Шаг | Поле warning | Поле stop |
|-----|--------------|-----------|
| CPC | `cpc_warning_percent_of_stop` | `cpc_stop_percent_of_base` |
| CPL | `cpl_warning_percent_of_stop` | `cpl_stop_percent_of_base` |
| CPR | `cpr_warning_percent_of_stop` | `cpr_stop_percent_of_base` |

Инпуты `type="number"`, min=1, max=100, step=1, placeholder="80". Пустое значение отправляется как `null`.

**Кнопки:**
- **Отмена** — закрывает без сохранения.
- **Сбросить на дефолты** — заполняет все 6 полей `null` локально (пользователь ещё должен нажать «Сохранить»).
- **Сохранить** — `PUT /offers/:id/rules` с 6 полями; остальные поля правил не трогаем.

**Загрузка:** при открытии модалки — `GET /offers/:id/rules`, заполняем поля. Пока грузится — показываем лоадер, кнопка «Сохранить» disabled.

**Закрытие:** по крестику/Escape/клику вне модалки — как обычная модалка.

  - Удалить компонент `ThresholdsBlock` и константы `THRESHOLD_STEPS` из `OffersPage.jsx`, если они больше не нужны нигде.
  - В `OfferModal` убрать секцию порогов полностью.
  - Добавить колонку «Пороги» с кнопкой «Настроить пороги» (стилистика кнопки — как остальные action-кнопки в таблице офферов).
  - Состояние `thresholdsFor: Offer | null` на странице; клик по кнопке → `setThresholdsFor(offer)`.
- Новый `frontend/src/components/offers/ThresholdsModal.jsx`:

  - Загружает правила через `getOfferRules(offer.id)`.

### API-клиент

- Никаких изменений — используем существующие `getOfferRules` / `updateOfferRules` в обоих фронтах.

## Обработка ошибок

- Ошибка загрузки правил → toast «Не удалось загрузить пороги», модалка закрывается.
- Ошибка сохранения → toast с текстом ошибки, модалка остаётся открытой.
- Успешное сохранение → toast «Пороги обновлены», модалка закрывается, `onSaved()` вызывает перезагрузку списка офферов (чтобы пересчитать «Правила»-колонку, если там отражаются пороги).

## Тестирование

- Ручной тест обоих фронтов: открыть модалку, изменить значения, сохранить, переоткрыть, убедиться что значения сохранены.
- Проверить «Сбросить на дефолты» + «Сохранить» → в БД должны стать дефолтные значения (80/80).
- Существующие unit-тесты API не затрагиваются.
- Pytest должен остаться зелёным (468 passed).
- `npm run build` в обоих фронтах должен проходить.

## План выката

Одна ветка → один коммит в main (уже работаем в main-режиме).
