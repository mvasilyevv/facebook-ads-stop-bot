# Как добавить или починить шаг автосоздания кампании

Этот документ — рабочий регламент. Использовать каждый раз, когда нужно
добавить новый шаг (`core/campaign_creator/steps/<name>.py`) или починить
сломавшийся существующий. Цель — чтобы запись recorder помогала, а не
диктовала; runner оставался статичным и предсказуемым.

## Модель: recorder ≠ runner

- **Recorder** (`core/campaign_recorder/`) — design-time инструмент. Жмёшь
  по нужным элементам в реальном Ads Manager, получаешь markdown-отчёт
  (`docs/campaign_recordings/<offer>.md`) со стабильными селекторами и
  семантическим контекстом виджета.
- **Runner** (`core/campaign_creator/`) — runtime. Никаких импортов из
  `core.campaign_recorder`. Шаги читают только `StepContext` + `params`
  и оперируют selectors, заданными прямо в коде шага.

Recorder подсказывает, runner исполняет. Эти миры связаны только через
человека-разработчика, который переносит знание из markdown в код шага.

## Workflow добавления нового шага

1. **Записать сценарий**. Запустить recorder, пройти руками нужный кусок
   UI (например, «настройка возраста»). Перед каждым логическим действием
   жать `Ctrl+Shift+M` (на macOS — `Cmd+Shift+M`) и вводить понятную
   подпись. Это разрезает сырой лог событий на блоки.

2. **Прочитать markdown-отчёт**. Открыть `docs/campaign_recordings/<offer>.md`.
   В каждом шаге смотреть:
   - `**Виджет:**` — семантическая роль кликнутого элемента (`combobox`,
     `button`, `tab`...).
   - `**Открылось после клика:**` — что появилось на экране.
   - `Селекторы (стабильные):` — кандидаты для копирования в код.
   - `Селекторы (нестабильные):` — только для отладки; в код **не** копируем.

3. **Выбрать селекторы для шага**. Порядок предпочтений:
   1. `[placeholder="..."]` для инпутов.
   2. `[aria-label="..."]` для меток.
   3. `role=button[name="..."]` / `role=option[name="..."]`.
   4. `text="..."` для коротких label.
   5. Scoped: `[data-pagelet="..."] >> text="..."` — если шаг живёт внутри
      конкретного pagelet'а.
   Никогда: `xpath=`, `data-auto-logging-id`, обфусцированные `xN`/`_N` классы.

4. **Создать модуль шага**. В `core/campaign_creator/steps/<name>.py`:
   - Локальные константы селекторов в шапке файла (как в `set_geo.py`):
     `SECTION_LABEL`, `<FIELD>_INPUT`, ...
   - Класс `<Name>Step(BaseStep)` с `name = "<name>"`.
   - `execute(self, page, context, params=None)` — должен поддерживать
     `params=None` (legacy-путь по `context`) и декларативный путь
     (`params={...}`).
   - Опциональные хуки `pre_check` / `verify` — если есть конкретное
     предусловие (нужный drawer открыт) или пост-проверка (значение
     попало в DOM). Если их не нужно — не переопределяй, есть no-op в
     `BaseStep`.

5. **Зарегистрировать в STEP_REGISTRY**. Добавить запись в
   `core/campaign_creator/steps/__init__.py` (или там, где сейчас живёт
   `STEP_REGISTRY`).

6. **Использовать humanizer для UI-операций**. Никаких сырых
   `page.mouse.wheel`, `get_by_text(...).first.click()` без сценария.
   Стандарт:
   - Клик по тексту/label/role → `human_click_label`.
   - Выбор опции в listbox/combobox → `human_pick_option`.
   - Ввод в input → `human_type` (если поле обычный input) или ручная
     цепочка `click → keyboard.press('Control+A') → keyboard.press('Delete')
     → keyboard.type(value, delay=...)` (для combobox-span'ов).

7. **Написать unit-тесты**. Минимум:
   - Идемпотентный путь: если уже всё как нужно — шаг не делает мутаций.
   - Декларативный путь: `params={...}` приводит к ожидаемым вызовам
     humanizer'а.
   - Один негативный кейс: нужный элемент не найден → понятная ошибка.
   Шаблон — см. `tests/unit/test_set_geo.py`.

8. **Прогнать локально**: `pytest tests/unit/ -q && ruff check .` Должны
   пройти все тесты, ruff чистый.

9. **Dry-run только когда блок готов целиком**. Не запускать live до
   окончания связанной группы шагов (например, «настройка кампании»
   или «настройка адсета»). Перед dry-run **обязательно** напомнить
   пользователю удалить старую тестовую кампанию вручную.

## Workflow починки сломавшегося шага

1. **Воспроизвести руками** в реальном Ads Manager. Если UI поменялся —
   запустить recorder, перезаписать сценарий нужного шага.
2. **Сравнить старый и новый markdown**. Что изменилось: placeholder?
   aria-label? появился ли промежуточный диалог?
3. **Обновить локальные константы** в шапке `<step>.py`. Не править
   `selectors.py` — его больше нет, селекторы лежат рядом со своим шагом.
4. **Если упал pre_check/verify** — это значит реальное состояние UI
   отличается от ожидаемого. Либо обновить хук, либо добавить шаг,
   приводящий UI в нужное состояние, прежде чем исполнять текущий.
5. **Добавить регрессионный unit-тест** на конкретную поломку.
6. **Пройти acceptance** — те же `pytest + ruff`.

## Чего НЕ делать

- Не импортировать ничего из `core.campaign_recorder.*` в `core.campaign_creator.*`.
- Не копировать селекторы из блока «Нестабильные» markdown-отчёта в код шага.
- Не использовать `page.mouse.wheel` для скролла внутри drawer'ов — у них
  свой overflow-контейнер. Скролл должен делать сам humanizer или
  `scroll_into_view_if_needed`.
- Не делать «авто-исправление состояния» в `pre_check`. Этот хук только
  валидирует и кидает исключение с понятным сообщением. Исправлять —
  задача `execute` или предыдущего шага в плане.
- Не добавлять глобальные модули селекторов. Шаг-специфичные константы —
  в шапке файла шага. Только селекторы, реально используемые ≥2 шагами
  (например, кнопка «Далее»), переезжают в `core/campaign_creator/ui/`.
- Не запускать live dry-run без согласования с пользователем и без
  напоминания удалить старую кампанию.
